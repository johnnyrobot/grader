# P0 — Engine Spike

**Goal:** prove a small local model can produce reliable, schema-valid rubric grades — before
we build anything on top of that assumption.
**Status:** ✅ **COMPLETE.** Tool-Output mode validated; two model decisions reversed by measurement.
**Why first:** every other phase assumes structured local grading works. If Tool-Output mode had
failed on quantized models, the whole agent design would have changed. Better to learn that in
week 1 than week 9.

## The four questions P0 exists to answer

| # | Question | Answer |
|---|---|---|
| 1 | Can a small local model drive **Pydantic AI's Tool-Output mode** for rubric JSON, or must we fall back to Prompted-Output? | ✅ **Tool mode works.** `qwen3:8b`: **100% schema success, 0 retries** across 4 submissions. No fallback needed. |
| 2 | Which model grades acceptably at the **16 GB tier**? | Text: **`qwen3:8b` ✅** correct rank-ordering (17 > 10 > 2 > 2). Vision: **Qwen3-VL is NOT viable — see below.** |
| 3 | Latency vs the PRD's **≤90s/essay** budget | ✅ text 27–66s. ❌ `qwen3-vl:4b` **140–263s** — blows the budget 3×. |
| 4 | Score stability at temp 0 | ✅ **spread 0.0** — deterministic, as the research predicted. |

## 🔴 P0 REVERSED A RESEARCH DECISION: drop Qwen3-VL for the vision path

The research picked **Qwen3-VL** on licence (Apache 2.0), benchmarks, and mlx-vlm LoRA support.
**Running it destroyed that choice.**

`qwen3-vl:4b` emits **20,000+ characters of `<think>` reasoning** to answer *"score this 0–5."*
~4,900 eval tokens of deliberation for a one-line judgment. And **the reasoning cannot be turned
off**: Ollama's `think: false` is ignored (identical thinking output), and Qwen3's documented
`/no_think` soft-switch is ignored too (20,566 chars with it). Both were tested.

Measured, same prompt, same machine, warm:

| Model | Latency | Eval tokens | Verdict |
|---|---|---|---|
| **`minicpm-v4.6`** (1.3B) | **5.8s** | 610 | ✅ **24× faster — use this** |
| `gemma4:e2b` | 10.3s | 407 | ✅ viable (but Gemma ToU licence) |
| `qwen3-vl:4b` | **140s** | 4,887 | ❌ unusable |
| `grader-vl:4b` full grade | **263s** | — | ❌ 3× over budget |

A 30-item handwritten batch on Qwen3-VL would take **2 hours**. On MiniCPM-V, ~3 minutes.

**Decision for v1: `minicpm-v4.6` for the vision path.** It's already in Ollama's official library
(1.3B, verified in the research). Qwen3-VL's advantage was mlx-vlm **LoRA** support — but
calibration is **retrieval-first**, so LoRA is a *v2* concern. Revisit then; don't pay 24× latency
now for a capability we've deliberately deferred.
**TODO before shipping:** confirm MiniCPM-V's licence terms for redistribution.

### The architectural consequence: transcribe, then grade

Don't ask the vision model to *judge*. Ask it to **transcribe**, then let the fast text model grade
the text. Short output = no reasoning spiral, and it keeps the grading logic in one model with one
calibration path.

```
handwriting image --[minicpm-v4.6: transcribe]--> text --[qwen3:8b: grade]--> GradeDraft
```

This also means the anchor-exemplar calibration works identically for handwritten and typed work —
one grading path, not two.

## What was built

- `engine/grader/schema.py` — `Rubric`, `RubricCriterion`, `GradeDraft`, `CriterionScore`.
  **The schema is the reliability mechanism**: Pydantic AI validates against it and re-prompts on
  failure, so anything expressible as a constraint is something the LLM *cannot* get wrong. Push
  rules into the schema, not into prompt prose.
- `engine/grader/agent.py` — the grading agent. Temp 0. Supports all three output modes.
  `validate_against(rubric)` catches what the schema can't (unknown criterion ids, out-of-range
  scores, missing criteria) and raises `ModelRetry` so the model repairs its own output.
- `engine/bench.py` — the benchmark. Uses the *real* Canvas sandbox rubric (4 criteria × 0–5) and
  four submissions spanning strong → barely-attempted.

## How to run

```bash
uv run python engine/bench.py                                    # default matrix
uv run python engine/bench.py --models qwen3:8b --modes tool --repeats 3
```

Reads: `engine/bench_results.json`. Columns: schema success rate, median seconds,
**rank-order correctness** (can it tell the four tiers apart?), and **temp-0 spread** (should be 0).

## Gotchas found

### 🚨 The context window, not the weights, decides whether the 16 GB tier works

`ollama ps` during the bench showed **`qwen3-vl:4b` consuming 41 GB**. A *four-billion-parameter*
model whose Q4 weights are only ~3.3 GB.

The cause: **Ollama loads a model at its full default context window.** Qwen3-VL advertises
**262,144 tokens**, so the KV cache alone eats ~38 GB. On the 16 GB machine the PRD targets, that
model would simply **fail to load** — and we'd have discovered it in P5, on a user's laptop.

Grading never needs that. Real budget: a 1,500-word essay (~1,950 tok) + rubric (~400) + 6 anchor
exemplars (~2,100) + system prompt (~300) + output (~800) ≈ **5,500 tokens**. The 262k default is
**16× more than we will ever use, at ~16× the memory cost.**

**Fix — `scripts/make_models.sh`** bakes capped variants (`num_ctx=16384`, `temperature=0`):
`grader-text:8b`, `grader-vl:4b`, `grader-vl:8b`. Capped, `qwen3-vl:4b` lands around ~6 GB — which
*fits*. **Always grade against the `grader-*` variants**, never the raw base tags.

Verify after any model change: run a grade, then `ollama ps`. SIZE should be single-digit GB.
If it shows tens of GB, the capped variant isn't being used.

### Other

- **Rank-ordering is the real test, not schema validity.** A model that emits perfect JSON but
  scores a strong essay the same as a weak one is useless. The bench checks ordering explicitly.
- `qwen3:8b` scored *weak* and *barely* both 2.0 — it separates the top three tiers cleanly but
  compresses the bottom two. Likely fine (both are failing work), but watch it.
- Model pulls are multi-GB — run them in the background before you need them.
- **The 64 GB dev machine is not the target.** The floor is 16 GB. This finding is exactly what
  that warning was for: everything looked fine on the dev box while being impossible on the target.
- Python buffers stdout when piped — use `-u` or expect an empty log until the run ends.
