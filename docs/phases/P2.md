# P2 — App Shell + Core UX

**Goal:** an installable `.app` that grades local folders end-to-end, keyboard-first.
**Status:** 🟡 **In progress.** Engine API, Tauri scaffold, Queue, Split view, Model manager, and
persistence layer are built. Frontend (tsc + vite) and Rust (cargo check) both pass. Not yet
wired as a running `.app` (sidecar integration, first-run download flow, and signing remain).
**Depends on:** P1 (the engine must grade well before a UI is worth building around it).

## Stack (decided — see RESEARCH.md §6)

- **Tauri 2** (Rust) + WKWebView — mature signing/notarization/updater, first-class sidecars, ~5 MB.
  *Deno Desktop 2.9 was evaluated and is real, but explicitly experimental (1 month old at research
  time). Re-evaluate at feature-freeze; the Python-engine boundary makes the shell swappable.*
- **React + TypeScript + Tailwind** for the UI.
- **Python engine** (FastAPI on localhost, loopback + per-launch token) — already exists in `engine/`.
  Everything AI/document/Canvas-related lives there; the shell is a client.

## The two screens that matter

**1. Queue (home).** Triage lanes from `grader/triage.py`:
`Review First (n)` · `Standard (n)` · `High Confidence (n)`.
The queue's job is to make 30 papers feel like 8. Show the payoff explicitly —
`QueueStats.summary()` already renders it: *"30 submissions → read 12 + spot-check 4 of 18 = 16 (47% less reading)."*

**2. Split view (grading).**
- **Left:** the original document rendered (PDF.js / docx render / page images with OCR overlay).
  The teacher must see *the student's actual work*, not just parsed text.
- **Right:** rubric scorer (per-criterion steppers + level anchors) · AI rationale (collapsible) ·
  feedback editor · citations panel · flags.
- **Every score links to its criterion and its anchor exemplars.** "Why this score" is one click:
  *"resembles these three you scored 4."* This is the trust mechanism — no unexplained numbers.

**Keyboard map:** `J/K` next/prev · `A` approve · `1–5` score focused criterion · `E` edit feedback ·
`F` flag · `⌘⏎` approve+next. Grading is a flow state; never interrupt it with modal churn.

## Also in P2

- First-run wizard: hardware detect → model tier → **resumable, checksummed download** → smoke test.
  (**Never bundle weights** — every comparable app downloads on first run; bundling means
  re-notarizing GBs per release. See `docs/research/04-lora-and-mac-packaging.md`.)
- Crash-safe job queue (SQLite/WAL): any interrupted batch resumes; no grade data loss on force-quit.
- Append-only audit log: model, prompt/rubric version, retrieved anchors, AI draft, confidence,
  teacher edits, timestamps. This is both the trust story and the FERPA story.
- SQLCipher at rest; Canvas token in Keychain.

## Design principles (from the PRD)

1. **The teacher's hand is always on the wheel** — AI output is visibly a *draft*; approval is an act.
2. **Show your work** — every score cites criterion + evidence + anchors.
3. **Attention where it matters** — high-confidence items collapse to spot-checks.
4. **Calm, keyboard-first, batch-friendly.**
5. **Privacy is visible** — persistent local-only indicator; a network panel showing every outbound category.

## Empty states teach the model

"Grade 3 yourself to unlock AI drafts" — the cold-start rule *is* the onboarding. It makes
calibration structural rather than optional.

## ▶ Build sequence (do these in order)

**1. Wrap the engine in FastAPI** (`engine/api.py`) — the shell talks to this, nothing else.
```bash
uv add fastapi uvicorn
uv run uvicorn engine.api:app --host 127.0.0.1 --port 8756 --reload
```
Endpoints to expose first (the rest can wait): `POST /grade/batch` · `GET /queue` ·
`POST /grades/{id}/approve` · `POST /grades/{id}/override` · `GET /models` · `WS /ws/jobs`.
Loopback only, per-launch bearer token. Reuse `grader.agent.grade`, `grader.triage.triage` as-is.

**2. Scaffold Tauri**
```bash
npm create tauri-app@latest -- --template react-ts   # into app/
cd app && npm install && npm run tauri dev
```
Register the Python engine as a **sidecar** (`tauri.conf.json` → `bundle.externalBin`) so it
starts/stops with the app. Ship the engine as a PyInstaller binary, or require `uv` at first run
(decide early — it affects packaging).

**3. Build the two screens** (see below). Queue first — it's the home screen and it's mostly a
table over `GET /queue`.

**4. Model manager + first-run wizard.** Detect RAM → recommend tier → `ollama pull` with progress →
run `scripts/make_models.sh` → smoke-test a grade → "ready".
**Do not skip the capping step** — see `docs/phases/P0.md`; an uncapped model can eat 41 GB.

**5. Persistence.** SQLite (WAL) for the job queue + audit log; SQLCipher for student content;
Keychain for the Canvas token.
